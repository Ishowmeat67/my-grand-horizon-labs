Architecture

One gateway, three focused services

Every request enters through the API Gateway and is routed to the service that owns that data. Each service talks only to its own database.

Dashed: the Booking Service looks up guests and rooms through their own APIs, never their tables.

Port 8000

API Gateway

The single door into the system. Routes auth, guest, room, hold and booking paths to the right service.

Port 3001

Guest Service

Registration and login with bcrypt-hashed passwords. Guests, staff and admins are separate roles.

Port 3002

Room Service

Room types, nightly rates, capacity and availability status, served from MySQL.

Port 3003

Booking Service

Holds a room for 15 minutes in Redis, then confirms it as a permanent booking in MongoDB.

Design

Decisions that make it reliable

  • Holds that expire on their ownAn abandoned reservation frees the room automatically through a Redis TTL, with no clean-up job.
  • Double-booking is blockedDate ranges are checked for overlap against confirmed bookings and other guests' active holds.
  • The server sets the priceRates come from the Room Service and add-on prices from the server, so the total can't be edited in the browser.
  • Booking snapshotsEach booking stores the room and rate the guest agreed to, so later price changes never alter it.
  • No secrets in codeEvery credential is read from environment variables and a git-ignored .env file.
  • Health-checked containersDocker Compose starts each service only when the databases it needs report healthy.
